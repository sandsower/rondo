# Agent Token Accounting

This document explains how agent adapters report token usage and how Rondo should account for it without double-counting repeated provider snapshots.

## Short Version

- Rondo preserves raw adapter usage events in the run ledger for diagnostics.
- Dashboard/API totals use normalized accounting, not a blind sum of every raw event.
- Claude Code compatibility events are treated as event deltas by the current adapter path.
- Pi usage events are treated as cumulative snapshots; Rondo adds only positive movement from the last accounted Pi snapshot.

## Primary Source Semantics

Adapters normalize provider usage into maps that may include:

- `input_tokens`: tokens consumed by the prompt/context
- `output_tokens`: tokens generated by the model
- `cache_read_tokens` / `cache_write_tokens`: provider cache tokens when available
- `total_tokens`: provider-reported or adapter-computed total
- `cost`: provider-reported cost when available

The meaning of a usage map is adapter-specific. Some providers emit per-event deltas; others repeatedly emit the latest cumulative session snapshot.

## Event Types

### Usage events from Claude Code

The Claude Code adapter path treats normalized usage maps as event deltas. Each usage event contributes fresh spend for the current invocation:

- `input_tokens`: input tokens for that event/invocation update
- `output_tokens`: output tokens for that event/invocation update
- `total_tokens`: total tokens for that event/invocation update

Rondo parses these events from subprocess stdout as they arrive and adds them directly to normalized dashboard/API totals. Raw events remain in `artifacts/agent-events.ndjson` for diagnostics.

### Usage events from Pi

The Pi adapter path treats usage maps as cumulative snapshots. Repeated Pi events may report the same latest session totals, so Rondo compares each snapshot with the last accounted snapshot for the same session/run ref and adds only positive movement. Raw events remain in `artifacts/agent-events.ndjson` even when normalized accounting collapses repeated snapshots to zero fresh spend.

### Session completion

When an adapter invocation completes, its final usage is recorded through the same adapter-specific normalization path. For continuations, Rondo accumulates normalized deltas across invocations while preserving each raw provider event.

## What The Metrics Mean

### Normalized totals

These are the primary accounting surface:

- Claude Code: sum of adapter event deltas
- Pi: positive deltas between cumulative snapshots
- Other adapters: whatever semantics their adapter declares and normalizes

Use these when you want:

- live dashboard totals
- stable per-run accumulation
- recovery without double-counting repeated snapshots

### Context window

The model's context window limit is not reported inline with usage events. It should be treated as a configuration constant based on the model in use, not derived from token spend.

For Rondo, context window size should be displayed or logged separately from spend.

## Recommended Accounting Strategy For Rondo

Track usage per active adapter session.

For each running issue, keep:

- normalized running totals exposed in UI/API
- the last reported provider snapshot for cumulative adapters such as Pi
- `last_seen_session_id` / run ref metadata when available

### Algorithm

#### When a usage event arrives

- Extract `input_tokens`, `output_tokens`, and `total_tokens`.
- For delta-style adapters, add the event usage directly.
- For cumulative-snapshot adapters such as Pi, compare against the last reported snapshot for the same session/run ref and add only positive deltas.
- If the cumulative counter decreases or the session/run ref changes, treat the new snapshot as a reset baseline for a new invocation.

#### When a continuation starts

- Preserve the normalized running totals accumulated so far.
- For delta-style adapters such as Claude Code, continue adding fresh event deltas from the new invocation.
- For cumulative-snapshot adapters such as Pi, reset the comparison baseline when the session/run ref changes or when provider counters decrease.

### Why this matters

If you treat per-invocation totals as global totals across continuations, you will undercount. If you blindly sum cumulative snapshots as deltas, you will overcount.

## What Rondo Should And Should Not Do

### Do

- Parse usage events from adapter stdout.
- Preserve raw usage events in the run ledger.
- Normalize dashboard/API totals according to adapter semantics.
- Key cumulative accounting by `session_id` / run ref when available.
- Accumulate across continuations by adding normalized deltas only.

### Do not

- Do not assume every usage map is fresh spend.
- Do not sum repeated Pi cumulative snapshots as deltas.
- Do not discard raw usage events just because normalized accounting collapses them.
- Do not reset accounting when a continuation resumes the same logical session unless the provider counters reset.

## Practical Interpretation For Rondo Logs

When reading raw agent usage output:

- Claude Code usage events with `input_tokens` / `output_tokens` / `total_tokens`
  - treated as additive event deltas by the current adapter path
- Pi usage events with `input_tokens` / `output_tokens` / `total_tokens`
  - treated as cumulative snapshots and delta-normalized for dashboard/API totals
- Process exit
  - final usage is interpreted through the same adapter-specific normalization rules

## Recommended Rondo Documentation Contract

If Rondo documents token reporting externally, the contract should be:

- Live token totals come from adapter-normalized accounting.
- Raw run-ledger events are diagnostic evidence, not billing totals by themselves.
- Token counts may be per-event deltas or cumulative snapshots depending on adapter.
- Pi repeated/cumulative snapshots are de-duplicated via positive deltas by session/run ref.

## Implementation Checklist

- Parse usage events from adapter output
- Preserve raw events in the run ledger
- Normalize cumulative snapshots to positive deltas
- Key totals by `session_id` / run ref when available
- Accumulate across continuations
- Do not double-count repeated usage snapshots
